# 营养膳食系统・队员任务要求与建议（v1）

> 项目：营养膳食（食谱研究）—— 面向 2 型糖尿病合并轻度高血压自理老人的拍照膳食评估与低钠稳糖食谱推荐
> 演示形态：**响应式网页应用**（笔记本浏览器演示为主，自适应平板/手机；无外部硬件，笔记本摄像头拍照即可）；答辩现场有网
> 周期：约 2 周，3 人
> 代码仓库：`D:\code\---`（GitHub：`https://github.com/nine-mirrors/---`），每人一个分支，每日提交
> 本文档随开发推进更新，接口字段变更必须先在群里同步



***

## 一、项目目标与总体架构

**核心链路：**

拍照 → 食物识别（Top3 + 分量）→ 营养计算（热量 / 碳水 / GL / 钠 / 钾 / 蛋白）→ 用户画像匹配 → 规则触发（规则 ID + 阈值 + 证据）→ 适老化话术解释 → 低钠稳糖食谱推荐 → 记录与周报

**架构（模块化单体，FastAPI + Vue3）：**



```
Vue3 前端（C 负责，另一 Agent 协助，先以 mock 数据独立开发）

&#x20;       │  HTTP /api

FastAPI 后端（模块化单体，模块间只通过 Service 调用）

&#x20; ├─ recognition  识别（B 交付，Mock 先行）

&#x20; ├─ nutrition    营养计算（A 交付，成分表查表 + GL）

&#x20; ├─ evaluation   规则引擎（A 交付，规则外置，带证据）

&#x20; ├─ explain      话术生成（C 交付，模板兜底 + LLM）

&#x20; ├─ recommend    食谱推荐（A 食谱库 + C 检索/RAG）

&#x20; ├─ profile      画像（A）

&#x20; └─ records      餐次记录/周报（A）
```

**四条铁律：**



1. 营养数值、超不超标只由查表和规则引擎给出；**LLM 只负责表达，不允许产生任何数值或医学判断**

2. 识别、LLM 都走适配器接口，Mock 先行；谁的模块没做完不阻塞其他人

3. 每条规则带 `规则ID + 阈值 + 证据出处`，结果页可追溯

4. 推荐只做 "替换" 不做 "单纯删减"（减主食必须同时补蛋白和蔬菜，防肌少症）

## 三、成员分工

### 成员 A：知识工程与后端

**任务清单（按优先级）：**



1. **食物成分表查询模块**

* 读取 `data\` 下 CSV（1677 条），处理脏数据：`Tr`= 微量记 0、`—`/ 空 = 缺失、`*`= 估计值

* 提供按 foodCode、按名称模糊查询；返回每 100g 可食部的能量 / 蛋白 / 脂肪 / 碳水 / 膳食纤维 / 钠 / 钾 / 钙

1. **营养计算模块**

* 单食物：每 100g 数值 × 重量

* 混合菜：按配料表逐料累加（参考做法：菜 = 配料列表 + 成品重量，营养按比例折算）

* GL 计算：`GL = 碳水(g) × GI / 100`；GI 取自 GI JSON，无 GI 的肉蛋菜不计 GL

* 输出见接口契约

1. **规则引擎（核心交付物）**

* 规则**外置为 JSON 或 YAML 文件**，每条含：id、适用人群、指标、阈值、严重级别、证据出处、话术模板键

* 至少实现：单餐 GL 超标、高 GI 主食、单餐钠超标、高钠密度食物、蛋白质不足、钾不足、蔬菜不足、搭配良好（正向）

* 输入 "营养汇总 + 画像"，输出命中规则列表 + 评分（红 -15 / 黄 -8 / 提示 -3，100 分起扣）

1. **食谱库**

* 结构化 15–30 道中式低钠稳糖食谱（优先从《成人高血压食养指南》和下厨房 MIT 语料筛选）

* 每道：菜名、配料（foodCode + 克数）、成品克数、做法步骤、标签（低钠 / 低 GL / 高蛋白 / 富钾 / 易咀嚼 / 主食）

* 用成分表逐菜算出每份营养并打标签

1. **FastAPI 接口 + 数据持久化**

* 按第四节契约实现全部接口；画像、餐次记录原型期用 JSON 文件即可

* 启动后 `/docs` 能看到并测试全部接口

1. **画像逻辑**

* 蛋白质目标：体重 × 1.2 g/kg（合并慢病老人口径）；BMI 计算

**验收标准：**



* 白米饭 200g（foodCode 012401x，GI 83）算出碳水约 52g、GL≈43，能命中 GL 超标规则

* 每条规则触发时返回的证据字符串能对应到具体指南

* 接口契约里的字段一个不少；`/docs` 可交互测试

* 食谱每道都能追溯到配料克数，不能出现 "适量 / 少许" 直接进计算

**给 A 的建议：**



* 先做 "单食物查表 + GL" 这一条最短链路，再做混合菜和规则，别一上来就铺 30 道菜

* 规则文件让医学内容可读，方便老师检查（这是答辩加分项）

* 食盐、酱油、烹调油成分表条目不全，可建少量 "伪食材"（盐 Na≈39340mg/100g、酱油 Na≈5757mg/100g、油 899kcal/100g）

### 成员 B：食物识别与评估算法

**任务清单（按优先级）：**



1. **确定类别集**：20–30 类最常见的中餐主食 / 家常菜（米饭、馒头、粥、面条、番茄炒蛋、清蒸鱼、炒青菜、豆腐等），与 A 对齐类别名与食物编码的映射

2. **数据准备**：

* 首选 CNFOOD-241 子集（Mendeley 直链，CC BY-NC，学术可用），每类选 30–50 张；不足的自己拍 / 搜图补

* 两周内不做一盘多菜检测（YOLO 风险高），先做单图分类

1. **模型**：DINOv2 **ViT-S/14**（Apache 2.0，约 85MB），冻结骨干，只训练顶部线性分类头（384→类别数）

2. **输出**：Top3 类别 + 置信度；分量先给档位（小 / 中 / 大），不做重量回归（Nutrition5k 是西餐，本项目放弃）

3. **适配器封装**：实现 `recognize(image_bytes) -> [{kind, id, name, confidence, weightG, gi}]`，与当前 Mock 完全同签名；后端通过配置一键切换 Mock / 真实模型

4. **简化 DBI\_22**：按日餐次把食物归到谷类 / 蔬菜 / 水果 / 奶豆 / 肉蛋 / 油盐，对照膳食宝塔推荐量输出负端分、正端分、膳食质量距（原论文：何宇纳等，营养学报 2024,46 (3):209-214）

**环境要点（重要）：**



* 本机是 **RTX 5060 Laptop（Blackwell 架构，8GB）**，必须装 CUDA 12.8 版本的 PyTorch：

  `pip install torch --index-url https://download.pytorch.org/whl/cu128`（安装前到 [pytorch.org](https://pytorch.org) 核对最新索引）

* 验证 GPU 可用：`python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0))"`

* DINOv2 加载：`torch.hub.load('facebookresearch/dinov2', 'dinov2_vits14')`

**验收标准：**



* 测试集 Top-1 准确率 ≥ 80%（20–30 类子集）

* GPU 单图推理 ≤0.5s，CPU ≤3s

* 识别结果置信度 <0.7 时前端会要求用户确认，模型侧要如实返回置信度，不许硬凑

* 后端切换 Mock / 真实模型只改一个配置项

**给 B 的建议：**



* 先跑通 "DINOv2 提特征 + 逻辑回归 / 线性头" 在 10 类上的全流程，再扩到 30 类

* 数据比模型重要：每类 50 张干净中餐图，胜过盲目加模型

* 移动端 / 边缘端不是目标，不做量化和 ONNX（除非时间富余）

## 六、硬件依赖功能：前端演示模式 + 产品化路线

我们没有外部硬件，凡依赖硬件的功能**原型阶段一律在前端用 mock 数据演示**，UI 上标注 "演示数据"，答辩讲成 "软件闭环已验证，硬件在产品化阶段对接"。后端数据结构要预留这些字段，将来接设备时不改接口。



| 功能（原型）            | 真实硬件（产品化）       | 对接方式（后续）                  |
| ----------------- | --------------- | ------------------------- |
| CGM 动态血糖曲线、餐后血糖反应 | 动态血糖仪（硅基 / 雅培等） | 厂商开放平台 API 或蓝牙读取          |
| 血压记录              | 蓝牙血压计           | BLE 标准协议（GATT 血压服务）       |
| 心率、情绪、步数、睡眠       | 手环 / 手表         | 华为 / 苹果健康、微信运动 API        |
| 体重趋势              | 智能体脂秤           | 蓝牙 / 厂商 API               |
| 自动识别食物重量          | 智能餐盘 / 称重勺      | 重量传感器 + BLE               |
| 餐前状态、语音问答         | 麦克风 / 智能音箱      | 浏览器 Web Speech API 已可真实实现 |

## 九、附录：术语表（英文缩写解释）

### 医学与营养



| 缩写 / 术语 | 全称 / 含义                                                            |
| ------- | ------------------------------------------------------------------ |
| T2D     | Type 2 Diabetes，2 型糖尿病（本项目画像字段 t2d）                                |
| HTN     | Hypertension，高血压（本项目画像字段 htn）                                      |
| 肌少症     | 老年人肌肉量流失、力量下降；蛋白质不足会加重，所以本项目强调每餐足量蛋白                               |
| GI      | Glycemic Index，血糖生成指数（0–100）。吃等量碳水时升糖越快 GI 越高；低 <55、中 55–70、高> 70  |
| GL      | Glycemic Load，血糖负荷 = 碳水克数 × GI ÷ 100。同时考虑 "吃多少" 和 "升糖快不快"，是本项目核心指标 |
| kcal    | 千卡（大卡），热量单位                                                        |
| mg / g  | 毫克 / 克，1g = 1000mg                                                 |
| mmol/L  | 毫摩尔每升，血糖的计量单位（健康人空腹约 3.9–6.1，餐后 2h <7.8）                           |
| BMI     | Body Mass Index，身体质量指数 = 体重 kg ÷ 身高 m²，用来判断胖瘦                      |
| DBI\_22 | 膳食平衡指数（2022 版），何宇纳等提出的中国人膳食评分方法                                    |
| LBS     | Low Bound Score，DBI 负端分：该吃够的没吃够（不足）                                |
| HBS     | High Bound Score，DBI 正端分：该少吃的吃多了（过量）                               |
| DQD     | Diet Quality Distance，膳食质量距：总体偏离程度，分越高越不均衡                         |
| DASH    | 国际公认的降压饮食模式（多蔬果、低脂奶、低钠）                                            |
| DRIs    | 膳食营养素参考摄入量；其中 PI 是预防慢性病的建议摄入量（如钾 PI=3600mg / 天）                    |
| WS/T    | 我国卫生行业推荐标准（如 WS/T 652—2019 是 GI 测定标准）                              |
| CGM     | Continuous Glucose Monitoring，动态血糖仪（贴在手臂上连续测血糖，本项目用前端模拟）           |
| 优质蛋白    | 氨基酸组成接近人体需要的蛋白质：鱼、虾、蛋、瘦肉、奶、大豆                                      |

### AI 与工程



| 缩写 / 术语           | 全称 / 含义                                                                             |
| ----------------- | ----------------------------------------------------------------------------------- |
| AI                | Artificial Intelligence，人工智能                                                        |
| LLM               | Large Language Model，大语言模型（如 DeepSeek、通义千问），本项目只让它做 "话术改写"                          |
| RAG               | Retrieval-Augmented Generation，检索增强生成：先从食谱库 / 指南检索相关内容，再让 LLM 基于检索结果回答，减少胡说         |
| Embedding（向量）     | 把文本变成一串数字，语义相近的文本数字也相近，用于 RAG 检索                                                    |
| bge-small-zh-v1.5 | 智源开源的中文向量模型（约 2400 万参数，CPU 可跑）                                                      |
| DINOv2            | Meta 开源的自监督图像特征模型，本项目用它做食物识别的骨干网络                                                   |
| ViT-S/14          | Vision Transformer Small/14：小型视觉 Transformer，14 表示把图片切成 14×14 像素的小块；约 2100 万参数，85MB |
| 骨干网络 Backbone     | 负责提取图像特征的主体模型；上面再接一个简单分类头（Classifier）输出菜名                                           |
| Top-1 / Top-3     | 模型给出的最可能第 1 个 / 前 3 个答案；Top-1 准确率即 "第一答案就猜对" 的比例                                    |
| 置信度               | 模型对识别结果的把握程度（0–1），低于 0.7 时让用户确认                                                     |
| Mock              | 模拟的假数据 / 假模块，在真实模块没做好前顶替，保证其他人并行开发                                                  |
| API               | Application Programming Interface，应用程序接口；前后端通过它通信（如 `/api/evaluate`）                |
| 适配器               | 一种设计模式：Mock 识别器和真实 DINOv2 识别器提供相同函数，切换时业务代码不用改                                      |
| FastAPI / uvicorn | Python 后端框架 / 运行 FastAPI 的服务器程序                                                     |
| venv              | Python 虚拟环境：给本项目单独一套依赖包，不污染系统                                                       |
| pip               | Python 包管理器（类似手机应用商店）                                                               |
| CUDA / cu128      | NVIDIA 的 GPU 计算平台 / 其 12.8 版本；5060 显卡必须装 cu128 版 PyTorch                            |
| PyTorch           | Meta 开源的深度学习框架（简称 torch）                                                            |
| SSE               | Server-Sent Events，服务器流式推送：让 LLM 回答像打字机一样逐字显示                                       |
| JSON / YAML       | 两种结构化数据文件格式：接口数据用 JSON，规则配置用 YAML                                                   |
| TTS               | Text-to-Speech，语音合成（把文字读出来）；本项目用浏览器自带的 Web Speech API                               |
| OpenAI 兼容接口       | 一套事实标准的调用格式，DeepSeek、智谱等都兼容，换供应商只改配置                                                |
